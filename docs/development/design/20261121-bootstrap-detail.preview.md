# 最后陈述 · 首版庭审模拟详细设计

状态为预览版，供实现与验收使用。需求来源为[初始设计](20261118-bootstrap.md)。2026-11-21 确认了证人询问顺序、裁决范围以及浏览器端技术路线。

## 1. 交付边界与原稿审阅

一次完整游玩从选择案件开始，到玩家看到法官宣读结果结束。玩家控制辩方。创作者可以制作角色、候选人池和案件，并单独运行某个庭审环节。这两个入口使用同一套引擎和内容格式。

| 原稿中影响实现的问题 | 实现口径 |
| --- | --- |
| 两方证人的询问步骤不对称 | 全部证人遵循引用方 → 对方 → 法官。引用方问完可说明所证何事，对方问完提交质证，随后法官询问、裁决 |
| 辩方举证段落写成读取控方列表 | 两方各有自己的有序清单。控方逐项举证，辩方自选子集和顺序 |
| 罪轻辩护与二元投票如何共存 | 单被告、单指控。辩方可以陈述减轻情节，票面只回答此项指控是否成立。结果为有罪、无罪或未达成一致 |
| 谁决定终局 | 12 位陪审员投票。法官每轮参与讨论，最多十轮。引擎计票，法官生成综合意见 |
| 角色主会话描述中断，创作界面缺少执行流程 | 第 5 节定义可见范围及会话提交点，第 7 节定义内容往返与调试入口 |
| 刷新、请求失败、案件被重新编辑时如何继续 | 第 6 节规定以已提交步骤和开局内容快照恢复 |

采用 TypeScript 静态网页、浏览器本地存档、YAML 内容包。下文选择 React + Vite、IndexedDB 和单文件交换格式作为实现方案。内置素材先交付一个可通关的虚构案件，包含控辩双方各一件物证和一名证人，能覆盖四条举证路径。法律背景沿用项目的[制度研究](../research/20261117-us-federal-criminal-jury-system.md)，法官进入评议和十轮截止均为本游戏规则。

## 2. 模块和依赖

| 模块 | 拥有的数据和职责 | 对调用者的接口 |
| --- | --- | --- |
| profiles | 解析、校验角色和案件，生成候选人，解析引用，构造开局快照 | validate、importPack、exportPack、resolveCase、drawJurors |
| courtroom | 持有本庭日志、角色会话、评议游标和项目裁决状态。以纯函数将已提交事件还原为读模型 | create、restore、execute、view、subscribe |
| model | 将角色任务转换为指定协议的请求，保留同次工具循环需要的协议消息，校验返回值 | generate(request, signal)，可注入脚本化替身 |
| play | 持有游戏阶段、两方清单进度、当前材料和步骤。决定正常流程的下一步 | availableActions、dispatch、resume |
| studio | 内容草稿、字段校验、预览、导入导出、测试场景 | 与 play 并列调用 profiles、courtroom |
| storage | 本地内容库、运行快照和事务提交 | load、commit(expectedRevision, changeSet) |

UI 组件消费可见的读模型。play 负责顺序，courtroom 校验庭审事实，例如在场证人、质证所属材料、投票者资格。录入一个事实或生成一条发言的处理函数只读当前状态，返回拟提交事件和会话变更。由一个事务同时提交引擎变更与 play 游标。studio 可以在满足引擎前置条件的独立测试庭中直接发命令。

## 3. 内容契约

每份独立资源带 schemaVersion（首版整数 1）、kind、id、title。id 是内容作者指定的稳定字符串，同 kind 下唯一。运行中的角色、提交材料、事件另有 runId 范围内的实例 ID。引用定义与本庭实际提交分开，避免把辩方未选择的材料带入庭审。

| 资源或嵌套记录 | v1 字段与约束 |
| --- | --- |
| role | function 为 judge、prosecutor 或 witness；profile 含 name、gender、ethnicity、age、occupation、income、personality、history。age 为正整数，其他为文本，允许以“未说明”描述非关键属性。publicBio 是可向玩家展示的简介 |
| juryPool | givenNames 按 gender 分组，familyNames 为姓名片段；gender、ethnicity、occupation、age、income、personality、history 各有选项数组。文本项为 {value,weight}，年龄与收入用 {min,max,weight} 整数闭区间，收入单位由池的 incomeUnit 说明 |
| case | defendant、charge、background、judgeId、prosecutorId、juryPoolId；opening 和 closing 各含 prosecution、defense 文本；prosecutionItems、defenseItems 为有序材料数组，可为空 |
| 两类材料公共字段 | id（案内跨两表唯一）、kind、title、introduction、opposingComment。introduction 为引用方首次介绍，opposingComment 为对方质证草稿 |
| evidence | description 是客观描述。introduction 表达取得经过、案件关联和证明目的 |
| witness | role 内嵌完整证人定义，privateFacts 记录证人知道的事实，supplement 为引用方询问后说明。introduction 只作出庭介绍。questions 按 prosecution、defense、judge 分三组，元素为 {question,answerHint}，允许空数组。answerHint 仅供证人回答相关问题时参考 |

文本按字段校验，陈述、介绍、客观资料、指控和身份引用必须存在且非空。补充说明、参考回答及私有事实允许空文本。陪审员各维度按正的有限权重相对抽样，姓名在对应列表内均匀抽取，数值段先选区间再均匀取整数。池必须覆盖所有可抽中的性别，范围有序且各维度非空。每席各取一段性格和经历，生成 12 个唯一席位 ID；同名者用席位号区分。存入抽样结果与种子，恢复直接读取结果。案件提交前检查引用存在、角色职能匹配、材料和证人 ID 唯一。

内置目录建议为 profiles/roles/{id}.yaml、profiles/jury-pools/{id}.yaml、profiles/cases/{id}/case.yaml。证人随各自案件维护。导出格式固定为下列顶层结构；空数组合法，导出案件时自动携带其法官、控方及候选人池，单独导出角色或池时只填相应数组。

```yaml
schemaVersion: 1
kind: contentPack
roles: []
juryPools: []
cases: []
```

导入器先解析整个包，再校验结构、重复 ID 和全部依赖（包括本地库）。失败返回字段路径和原因，库保持原状。相同 ID 且内容一致则复用，有差异则显示冲突，由创作者选择覆盖或取消整包；内置资源只读，须另存新 ID 并同步重写包内引用。一次事务应用全部改动。导出再导入空库后，资源 ID、数组顺序、角色私有字段与草稿应逐项相等。

## 4. 运行接口与游戏流程

```ts
type Envelope = {
  runId: string
  commandId: string
  expectedRevision: number
  command: CourtCommand
}
type Receipt = { revision: number; eventIds: string[] }
interface Courtroom {
  execute(input: Envelope, signal?: AbortSignal): Promise<Receipt>
  view(): CourtView
  subscribe(onCommit: (receipt: Receipt) => void): () => void
}
```

create 接收固定的内容快照、随机种子、模型适配器和存储接口；restore 从同一存储恢复。命令可按下表实现为带 type 的联合类型。记录类命令接收已确认的正文，生成类命令由引擎取上下文。所有材料操作传入提交后的 itemId；offer 传入 definitionId 和 introduction，回执中的提交事件含新 itemId。法官裁决结构为 {itemId, admitted, reason}，采纳和排除都须给出理由。

| 阶段 | play 驱动的命令及界面行为 | 完成条件 |
| --- | --- | --- |
| 1 选定陪审团 | selectJury 从池生成并展示 12 张席位卡 | 12 个席位一次入账 |
| 2 控方开场 | recordOpening(prosecution, text) 直接录入案件文本 | 有且仅有一份控方开场 |
| 3 辩方开场 | 玩家预览、编辑并确认，recordOpening(defense, text) | 非空提交后锁定 |
| 4 控方举证 | 按数组顺序 offer，逐项执行下表 | 全部处理完毕，执行 closePresentation(prosecution)；空表直接执行 |
| 5 辩方举证 | 展示可选卡片，客观信息只读；玩家编辑引用说明、确认 offer；可主动结束举证 | 没有未决材料，执行 closePresentation(defense) |
| 6 控方结案 | generateClosing，基于庭审事实和控方草稿生成 | 控方结案正文已提交 |
| 7 辩方结案 | 展示草稿，编辑并 recordClosing(defense, text) | 辩方结案正文已提交 |
| 8 评议 | beginDeliberation 校验双开场、双方已结束举证、所有已提材料均有裁决、双结案；stepDeliberation 每次推进一个发言、指引、投票或综合意见 | 已计票并成功提交综合意见，展示结果 |

一次仅处理一项，已提交卡不能再次提交。下表每个箭头都是明确的 UI 进度点。玩家可零次或多次询问，点“结束询问”退出。玩家质证可选用草稿、改写或明确提交“无异议”。

| 材料 | offer 后到下一项前的步骤 |
| --- | --- |
| 控方物证 | 辩方 recordComment → 法官 rule |
| 辩方物证 | 控方 generateComment（参考对应草稿）→ 法官 rule |
| 控方证人 | 控方 examine → recordSupplement（案件预设）→ 玩家 ask 或结束 → 辩方 recordComment → 法官 examine → 法官 rule |
| 辩方证人 | 玩家 ask 或结束 → recordSupplement（预览可改、可跳过）→ 控方 examine → 控方 generateComment → 法官 examine → 法官 rule |

ask(itemId, question) 调用当前证人并成对记录一问一答。examine(itemId, actor) 让控方或法官在主会话中使用 askWitness 工具，只绑定当前证人。每一自动询问段先完成一次问答，然后可追加，默认最多三问，达到上限时结束该段。问题字段要求非空。引用方的补充说明可跳过时记录本步骤已结束，以便恢复。证人裁决针对该次出庭的整组证言。发言一经提交只读，点击预览、切换卡片或关闭编辑框均不产生庭审事件。

## 5. 日志、角色与评议

每条事件有 seq、type、actorId、audience、payload，材料相关事件另有 itemId。seq 在本庭中递增。日志覆盖选任、陈述、材料提交、成对问答、补充、质证、裁决、举证结束、评议发言、指引、投票、计票与宣告。主会话保存角色自己已经提交的交互、可续聊的私有状态和 lastSeenSeq。临时会话从主会话快照派生，用于独立试问或预览，结束后丢弃。正式生成时暂存角色变更，成功提交才推进主会话。供应商可用的私有续聊项仅归对应角色；公开记录只采集显式发言字段。

| 消费者 | 可以取得的信息 |
| --- | --- |
| 游戏 UI | 已公开的出庭资料、发言、裁决；辩方自己的手牌及可编辑草稿；评议进度和最终结果 |
| 控方、法官、陪审员 | 中立背景、本人档案及任务、其可见的庭审增量；仅执行当前动作时附上本方本环节草稿 |
| 证人 | 中立背景、本人档案与 privateFacts、自己的参考回答、从本次出庭至裁决前可听到的公开增量及当前问题 |
| 评议参与者 | 全部已采纳材料及其 ID、排除清单、双方结案、可见的本轮和既往讨论。投票时看不到本轮他人的票 |
| 创作 UI | 可编辑定义的全部字段，含私有事实；从独立测试庭查看各角色实际输入 |

构造角色请求时先装入系统层的角色、背景、私有事实和本次到庭任务，再合并本人历史、上次游标以后的可见事件、当前草稿和指令。按事件 ID 去重，避免本人发言同时出现在历史与增量中。证人首次游标从 offer 的位置开始。证人答案提示不随问题发送给提问人，辩方卡片不展示证人私有材料。隔离边界是游戏展示和请求构造；创作者本来就能读取本地 YAML。

评议开始时建立裁决索引。每次提示区分已采纳材料、程序记录、双方主张与中立背景。原庭审日志保留，评议中引用材料须给出已采纳的 itemId；受排除的证言及物证不能作为定罪或无罪依据。陈述和质证中转述材料也受同一规则约束。校验无效 ID 后要求重新生成；文字中误解事实由下一次法官指引纠正。上下文过长时暂停并提示换用更大上下文配置，保留游标和历史。

每轮固定按席位 1 至 12 发言，后一席能看到前一席。法官读取十二条评论，指出对证据或证明标准的误解。此后 12 人依据相同的轮末公共记录和各自私有会话投票，票值仅 guilty 或 notGuilty。每席每轮只接收一票，齐票才发布汇总。12 比 0 或 0 比 12 即结束；否则公布票数并开始下一轮。第十轮先检查一致，再判断 hung。引擎将确定的 outcome 交给法官撰写意见，界面从计票记录显示结论。综合意见生成失败可单独重试。案件结果不含量刑。

## 6. 模型接入、事务和恢复

配置项为协议、Base URL（包含版本前缀）、模型名和 API Key。页面向玩家显示请求目标，Key 仅保存在当前页面内存中，刷新后重新输入。配置页提供一次文本和工具往返测试，区分鉴权失败、模型不支持工具、返回格式错误以及浏览器无法访问端点。最后一种情况展示目标地址并提示检查网络与跨域设置。由统一客户端适配层对接这三条路径；实现时优先验证 AI SDK 的 OpenAI 和 Anthropic provider，在 model 内显式选择协议。浏览器真实端点验收通过后锁定依赖版本。[协议调查及依据](../research/20261121-browser-llm-tools.md)

| 项目 | 接口约定 |
| --- | --- |
| 请求 | generate 接收 actorId、任务名、系统提示、角色可见历史、当前输入、允许的工具或期望的结果结构，接受 AbortSignal |
| 返回 | 文本、工具请求或结构化结果，另带本次续聊所需的供应商记录。文本去空白后须非空；裁决检查布尔值及理由，投票检查枚举，材料引用检查归属。拒答、截断或格式错误均为本步骤失败 |
| 工具往返 | 仅 examine 注册 askWitness({question})。若一轮给出多个调用，按返回顺序校验和执行，超额或非法调用返回错误结果。每个调用 ID 对应一个结果。证人只看到自己的角色输入；问答回交提问者。仅模型提出且证人已回答的问题可以进入庭审日志 |
| 提交单位 | 一段自动询问最多三问，暂存其提问人及证人会话、工具调用与成对问答，整段成功后一次提交。玩家手动询问每一对单独提交。UI 中显示的生成进度须与已提交记录区分 |
| 失败与取消 | 用户可暂停后重试。无有效问答且模型结束、非法工具循环或超出预算均停止该步骤；每段最多四次提问者模型调用。取消使迟到的响应失效。重试从最近已提交步骤开始，未提交的请求可能再次产生供应商费用 |

本地保存三类对象：内容库、正在编辑的内容草稿、庭审存档。每庭存档含格式版本、runId、案件与角色快照、席位、事件、角色会话、流程游标和已完成命令回执。设置页单独管理非密钥连接配置。创作包只含定义。游戏中正在编辑的辩词按 runId、阶段和 itemId 自动保存，成功提交后清除。

每个动作先生成 commandId，并绑定请求内容与 expectedRevision。内存中同庭一次只运行一个命令。网络返回后开启短 IndexedDB 读写事务，先查同 ID 回执（参数相同则返回，参数不同报错），再比较 revision。相符才一起写入事件、角色变更、流程游标、回执并递增 revision。跨页竞争的失败方重载已提交记录。存储不足、请求失败或页面在事务前退出，均从上一次成功提交处恢复。已持久化的结果不重新调用模型；无法恢复的在途生成由玩家再次触发。

## 7. 两个界面的操作路径

**游戏。** 首页选择案件、配置模型或继续某庭。开庭页展示被告、指控与中立背景；庭审页展示当前阶段、已提交记录、材料详情及当前可执行动作。证人窗口提供参考问题与自由输入框，只显示当庭回答。玩家可分别查看已采纳和已排除材料。生成中显示发言人、步骤及取消入口；失败保留当前卡片与玩家草稿。评议显示轮数和席位进度，终局显示三态结果、末轮票数和综合意见。

**创作。** 在内容库中新建或复制资源，编辑角色字段、候选池权重、案件背景、双方草稿、材料顺序和证人私有信息。编辑器区分“玩家可见”“角色私有”“参考草稿”。预览可切换玩家、证人或提问者视角。草稿可以未填完，发布到本地可玩库时执行第 3 节校验；错误链接到具体材料与字段。库中的导入和导出走相同校验器。编辑已开庭的案件只影响以后新开的庭。

**快速调试。** 创作者选择案件、材料、目标环节（询问、质证、裁决、最终陈述或评议）以及测试模型。构造器从快照创建全新 runId，用与正式游戏相同的记录命令填入所需前序事实；耗模型的前置输出由创作者填写或选择明确标记的样例记录。比如测试证词裁决须先提供该证人的出庭信息、三方询问完成记录、问答和质证；测试评议须提供两方结案及各已提交材料的裁决。准备页展示将要注入的事实并提示缺项。目标动作使用正式引擎；重跑从同一夹具重新开测试庭，允许对比不同草稿和模型输出。测试庭独立存储，不覆盖玩家进度。

## 8. 开发顺序和验收

| 里程碑 | 可独立交付的切片 | 验收方法 |

| M1 内容与读模型 | 类型、YAML 解析、校验、内置角色／池／虚构案件、事件归约器 | 固定种子产生同一组席位；错误引用定位到具体字段；导出案件后在空库还原 |
| M2 可离线验证的引擎 | 注入脚本模型，实现录入、询问、裁决、投票以及恢复事务 | 跑通四条举证路径；核对每次发言的 actor、材料 ID 与角色实际输入 |
| M3 接入模型 | 配置页、三协议适配、工具调用与错误处理 | 从浏览器对每个协议选一组可用端点与模型，验证一次证人往返、裁决与投票，记录测试组合。用替身覆盖拒答、截断、超时及非法结果 |
| M4 游戏流程 | 静态页、阶段驱动器、回看、取消和续局 | 从首页完整游玩；跳过全部辩方材料仍能结案；重开页面能继续未完成步骤 |

用于验收的最小回归场景：

1. 控辩双方各提交一物证一证人。检查两名证人的首问方相反、末问方均为法官；播放器展示实际提交的辩方修改稿。已提交物证不能重复选择，待裁决时不能结束举证。
2. 给证人私有事实、另一方未提交的手牌、出庭前一句发言分别加唯一标记。检查实际发往模型的消息、工具结果及玩家视图，只在第 5 节允许的位置出现标记。证人主动在庭上说出的内容自该问答提交后才公开。
3. 在控方自动询问第二问断开网络，重载并重试。已完成的前序材料保持不变，本段只出现一次完整问答序列。两页同时点同一卡片只提交一次。导出包和存档均不含 API Key。
4. 用脚本投票分别制造首轮全票无罪、第十轮全票有罪、连续十轮分票。断言结果、票数、轮数以及每轮法官指引的位置；在第十一席投票后重载，仅补剩余席位。综合意见生成失败后重试，计票记录保持唯一。
5. 排除一项证据后让模型引用其 ID 作为裁决依据，校验拦下该输出；保留原庭审记录供回看。一方仍有未决材料或缺少最终陈述时，直接请求评议应返回缺少的条件。
6. 导入包含坏引用的包，检查库无部分写入；编辑原案件后重新打开旧庭，仍能用开局版本续玩。创作调试跑完一轮评议后，返回玩家庭，事件序列和游标与离开时一致。
