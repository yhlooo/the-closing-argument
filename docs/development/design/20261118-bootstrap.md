# 项目初始设计

## 0 整体架构

注意这里指代的模块名称都是指内部代号，并非展示给用户的文案。

从上到下分层：

- WebUI
  - GameInterface
  - CreationInterface
- CourtroomSimulationEngine
- RoleProfiles / CaseProfiles

## 1 WebUI

该游戏完全在浏览器端运行，通过 WebUI 呈现。

包含两个主要的界面：

- 游戏界面 (GameInterface)

  按照正常游戏流程进行法庭模拟的游玩界面。

- 创作界面 (CreationInterface)

  用于游戏创作者和玩家自定义编辑、导入、导出角色定义、案件定义。并便捷地对法庭特定环节进行快速调试，无需完整的游戏流程。
  这不仅是一个内部设计工具，也是一个可供玩家参与共创游戏内容的模块。

### 1.1 游戏过程

玩家在游戏中扮演辩方律师

1. 挑选陪审团成员
   1. 调用 CSE 挑选陪审团成员
   2. 将结果展示在界面上
2. 控方开场陈述
   1. 从案件定义中提取控方陈述内容
   2. 调用 CSE 记录控方陈述，并将该内容展示在界面上
3. 辩方开场陈述
   1. 从案件定义中提取辩方陈述内容
   2. 玩家点击“辩方陈述”，以预览可编辑的形式将预定义陈述内容展示在界面上，玩家可以按需修改，然后提交
   3. 调用 CSE 辩方陈述以录入内容
4. 控方举证环节

   从案件定义中提取控方证据、证人列表，按顺序提交，对于每一项证据、证人进行以下步骤：

   对于证据：

   1. 在界面上展示证据信息，包含客观信息和控方对于该证据的解释。调用 CSE 记录该证据。
   2. 玩家点击“提交质证意见”，以预览可编辑的形式展示预定义辩方对该证据的质证意见，玩家可以按需修改，然后提交。调用 CSE 记录质证意见。
   3. 调用 CSE 生成证据裁决，在界面上显示法官是否采纳该证据的结论和原因。
 
   对于证人：

   1. 在界面上展示证人信息，包含客观信息和控方对于该证人的初步解释（不含所证何事）。调用 CSE 记录该证人。
   2. 调用 CSE 触发辩方提问证人。界面展示提问和回答。
   3. 界面展示控方对以上证人证言的解释（所证何事）。调用 CSE 记录补充说明。
   4. 玩家此时可以按需打开与证人的对话框向证人提问。在提问界面可以自由问答也可以选择案件定义中预定义的辩方提问，调用 CSE 生成证人回答。
   5. 玩家点击“提交质证意见”，以预览可编辑的形式展示预定义辩方对该证人证词的质证意见，玩家可以按需修改，然后提交。调用 CSE 记录质证意见。
   6. 调用 CSE 触发法官提问证人。界面展示提问和回答。
   7. 调用 CSE 生成证人证词裁决，在界面上显示法官是否采纳该证词的结论和原因。

5. 辩方举证环节

   从案件定义中提取控方证据、证人列表，以卡片的形式在界面上进行展示。玩家可以按需点击浏览详情，决定是否提交。
   对于玩家决定提交的每份证据、证人，进行以下步骤：

   对于证据：

   1. 在预览界面展示证据客观信息和预定义的辩方对于该证据的解释，玩家可以对解释进行按需编辑，但不能修改客观信息，然后提交。调用 CSE 记录该证据。
   2. 调用 CSE 生成控方质证，在界面展示质证意见。
   3. 调用 CSE 生成证据裁决，在界面上显示法官是否采纳该证据的结论和原因。

   对于证人：

   1. 在预览界面展示证人客观信息和预定义的辩方对于证人的解释，玩家可以对解释进行按需编辑，但不能修改客观信息，然后提交。调用 CSE 记录该证据。
   2. 在与证人的对话框中玩家可以按需向证人提问。在提问界面可以自由问答也可以选择案件定义中预定义的辩方提问。调用 CSE 生成证人回答。
   3. 提问结束后玩家可选补充信息说明该证人证言所证何事（预览预定义内容可编辑）。调用 CSE 记录补充说明。
   4. 调用 CSE 触发控方提问。
   5. 调用 CSE 触发生成控方质证意见。
   6. 调用 CSE 生成证人证词裁决，在界面上显示法官是否采纳该证词的结论和原因。

6. 控方最终陈述

   调用 CSE 生成控方最终陈述

7. 辩方最终陈述

   界面显示辩方最终陈述草稿，玩家可编辑，提交。调用 CSE 记录。

8. 陪审团审议

   调用 CSE 发起陪审团审议，界面展示最终结果。

## 2 法庭模拟系统 (CourtroomSimulationEngine, CSE)

这是游戏的核心。包含一组易于集成的方法接口，在运行时初始化的对象中保持一组法庭状态。

包含以下主要子模块：

- **统一 LLM 调用框架**

  支持用户配置 BaseURL 和 APIKey 使用 OpenAI Chat Completions API / OpenAI Responses API / Anthropic Messages API 访问 LLM

  并将对 LLM 的调用抽象为一个统一接口，建议使用一些轻量的被广泛使用的库

- **角色模拟**

  基于通过角色定义和法庭上下文组合角色上下文（参考 [角色上下文模版](#21-角色上下文模版) ），调用 LLM 进行对话生成。模拟角色发表意见、参与讨论、回答问题等行为。

  每个角色应该有主会话和临时会话。在主会话上下文中按顺序包含这个人从法庭开始

- **法庭上下文管理**

  记录法庭从开始到结束期间所有人的发言、提交的证据、证据是否被法庭采纳、选择的陪审团成员、陪审团的讨论、最终结果等所有上下文信息。
  用于为每个角色提供关于法庭上发生事情的上下文信息。

  注意：每个角色的发言正文会记录入法庭上下文，但是其思考内容只留在角色自己的上下文中不与任何其它法庭成员共享。法庭上下文中只记录对法庭上每个人都公开的信息。

- **法庭事件模拟**

  一组无状态的方法，用于串联角色和法庭上下文的交互事件。包括：

  - **生成陪审团成员** ：随机产生 12 个陪审团成员录入法庭上下文（后期可扩展添加控辩双方对陪审团成员进行排除的过程）
  - **记录控辩双方开场陈述** ：直接录入陈述内容到法庭上下文，不触发其它交互
  - **记录证据、证人** ：直接录入证据、证人信息进入法庭上下文，包括控辩双方证据、证人。输出证据 ID ，作为后续提问、质证、裁决的引用。
  - **提问证人** ：触发控方或法官对证人进行提问。输入包括证人 ID ，让谁提问，调用控方代表或法官的角色模拟进行提问，在控方或法官的主会话中通过工具调用证人进行回答。
  - **生成证人回答**

    输入包含谁提问、提问哪一个证人、问题内容。调用证人的角色模拟输出回答。提问和回答作为证词记入法庭上下文。

    对于控方、法官对证人的提问，一般是由控方、法官的会话通过工具调用触发的，对于辩方的提问一般是在 UI 上由玩家触发的。
  
  - **生成控方质证**
  
    一般在辩方证据最终提交前触发，通过控方代表角色模拟生成对指定证据、证人的质证意见作为输出。质证意见录入法庭上下文。

  - **记录辩方质证**
  
    输入辩方对某控方证据或证人的质证意见，直接录入法庭上下文。

  - **生成证据、证人证词裁决**

    输入证据、证人 ID ，通过法官角色模拟生成对该证据、证人是否有效的裁决结果，如果无效需要附带原因说明。录入法庭上下文。
  
  - **生成控方最终陈述**

    调用控方角色模拟生成最终陈述，并录入法庭上下文
  
  - **记录辩方最终陈述** ：直接录入陈述内容到法庭上下文，不触发其它交互
  - **陪审团讨论**

    每位陪审团成员基于已知信息和自己对案件的理解按顺序发表一轮评论。
    然后法官基于所有评论发表专业意见，可以补充必要的法律专业知识，纠正陪审团成员对信息的错误理解（比如以未被采纳的证据作为理由，未被采纳的证据应该完全排除）。
    然后每位陪审团成员进行投票（被告是否有罪）。如果投票达成一致则讨论结束，由法官综合所有陪审团成员的发言输出一份包含结果的陪审团综合意见。
    如果投票未能达成一致则重新回到讨论环节，继续 每位成员按顺序发言 -> 法官发言 -> 投票 的循环。直到所有陪审团成员投票达成一致。或者连续进行 10 轮仍为达成一致。
    如果最终结果是未能达成一致，那么仍然由法官生成包含未能达成一致的结果和陪审团成员的综合意见。

不包含：

- 法庭模拟系统本身不包含任何角色定义和案件定义。它们由 RoleProfiles 和 CaseProfiles 模块提供，在初始化时设置。
- 不包含游戏进程的驱动逻辑（比如什么时候应该由谁发表陈述、由谁举证），法庭模拟系统所模拟的法庭状态由外部调用驱动改变，但是可以包含一些必要的上下文校验（比如必须所有陈述、举证、质证都完成后才能进入陪审团评议，因为这是陪审团评议的必要）
- 不包含任何显示界面实现

上面提到的控方行为和辩方行为流程不完全一致主要是由于控方部分信息是案件定义中已经包含的，辩方信息是玩家产生的。


## 3 角色定义 (RoleProfiles)

可插拔的关于游戏中法官、陪审团成员及候选人、控方代表、证人的角色定义。定义决定这些角色的表现、思维、行动风格。

每一个角色定义都包含其基础信息（姓名、性别、族裔等）、性格、人生经历、社会身份（工作、收入等）等信息定义。具体定义结构待定。

角色包含 3 大部分，在项目中的定义方式不同：

- 法庭成员

  包括法官、控方代表。系统应提供一组内置的默认预设，对于每个所需的角色有一份完整的定义。

- 陪审团候选人池

  为了提供充足的陪审团候选人，采用运行时随机组合的方式生成具体的候选人定义，而不是逐人完整预定义。

  但是仍需对构成完整角色定义的每个部分提供一组预定义选项。
  比如若干男性 First Name 、若干女性 First Name 和若干 Last Name 用于组合姓名，若干可以组合的性格、人生经历片段用于组合完整性格描述。
  工作、族裔、收入、年龄等在真实人群中具有分布特征的项除了需要提供可选列表，也要添加权重定义。收入、年龄等数值可以使用数值段+权重进行定义。

- 案件证人

  证人需要逐个完整定义，但由于证人与具体案件相关，因此属于案件定义的一部分。

系统默认预设应使用 YAML 格式在项目中集中定义，便于集中查看和修改，每个完整的角色定义一个文件，陪审团候选人池一个文件。在代码中引用这些定义。

## 4 案件定义 (CaseProfiles)

可插拔的关于游戏中模拟审理的案件的定义。定义决定法庭模拟系统向游戏内角色、玩家展示的案件相关信息内容。

每一个案件定义应该包含以下内容：

- 案件背景信息

  在审理开始前法庭上所有人应该周知的关于案件的已知信息。它是完全中立的，只包含无争议的事实（比如案件导致几人死亡），不包含尚待证明的推论（比如凶手就是被告）。

- 控方开场陈述

  控方对案件过程的理解，认为被告有罪的理由，建议的量刑等。

- 辩方开场陈述

  任何可以在法庭上进行陈述的内容，目的是表明被告无罪或轻于控方指控的罪。

- 证据、证人

  按顺序定义的若干证据、证人。控方和辩方的证据、证人列表分别定义。控方证据、证人用于证明被告犯有控方指控的罪，辩方证据、证人用于证明被告无罪或轻于控方指控的罪。

  证据定义包含：
  - 引用方对该证据的解释。包含：证据与案件的关系，在什么时间、什么地点、通过何种方式取得，引用该证据是为了证明何事等
  - 证据的客观描述（具体是什么，什么样）
  - 对方对该证据的提前准备的质证意见（证据在庭审前已经提前知会了控辩双方，控辩双方因此可以提前准备质证意见，但是法庭上可以视情况修改）

  证人定义包含：
  - 引用方对该证人的解释。包含：证人与案件的关系，引用该证人是为了证明何事等
  - 控方、辩方、法官对证人的参考提问和证人的参考回答（可能出庭的证人在庭审前，已经提前知会了控辩双方，控辩双方因此可以提前准备提问，证人也可以提前准备对应的回答，但是法庭上可以视情况修改）
  - 证人的角色定义（见 RoleProfiles ），用于驱动证人回答提问
  - 证人自己真实了解到的案件相关信息（比如目击内容）这不会直接提供到法庭上，只用于驱动证人回答提问
  - 对方对该证据的提前准备的质证意见（可能出庭的证人在庭审前已经提前知会了控辩双方，控辩双方因此可以提前准备质证意见，但是法庭上可以视情况修改）

- 控方提前准备的最终陈述

  庭审前控方在该环节准备的发言内容，在法庭上可以视情况修改。重申被告的罪证，呼吁陪审团和法官公正判决等。

- 辩方最终陈述

  庭审前辩方在该环节准备的发言内容，在法庭上可以视情况修改。为被告无罪或罪轻做最后争取，表达对受害人的同情，呼吁陪审团和法官公正判决等。

案件定义中由辩方律师提供的陈述、解释等内容用于向玩家提供一个默认选项，玩家在游玩时提出前可以按需修改。由控方、法官、证人提供的提前准备的发言内容作为这些角色模拟的参考回答，用于辅助生成。

系统默认预设应使用 YAML 格式在项目中集中定义，便于集中查看和修改，每个案件一个目录，其中按合理结构组织文件。
