# 项目初始设计

## 0 整体架构

注意这里指代的模块名称都是指内部代号，并非展示给用户的文案。

从上到下分层：

- WebUI
  - GameInterface
  - CreationInterface
- CourtroomSimulationEngine
- RoleProfiles / CaseProfiles

## 1 WebUI

该游戏完全在浏览器端运行，通过 WebUI 呈现。

包含两个主要的界面：

- 游戏界面 (GameInterface)

  按照正常游戏流程进行法庭模拟的游玩界面。

- 创作界面 (CreationInterface)

  用于游戏创作者和用户自定义编辑、导入、导出角色定义、案件定义。并便捷地对法庭特定环节进行快速调试，无需完整的游戏流程。
  这不仅是一个内部设计工具，也是一个可供玩家参与共创游戏内容的模块。

## 2 法庭模拟系统 (CourtroomSimulationEngine, CSE)

这是游戏的核心。包含一组易于集成的方法接口，在运行时初始化的对象中保持一组法庭状态。

包含以下主要子模块：

- **统一 LLM 调用框架**

  支持用户配置 BaseURL 和 APIKey 使用 OpenAI Chat Completions API / OpenAI Responses API / Anthropic Messages API 访问 LLM

  并将对 LLM 的调用抽象为一个统一接口，建议使用一些轻量的被广泛使用的库

- **角色模拟**

  基于通过角色定义和法庭上下文组合角色上下文（参考 [角色上下文模版](#21-角色上下文模版) ），调用 LLM 进行对话生成。模拟角色发表意见、参与讨论、回答问题等行为。

  每个角色应该有主会话和临时会话。在主会话上下文中按顺序包含这个人从法庭开始

- **法庭上下文管理**

  记录法庭从开始到结束期间所有人的发言、提交的证据、证据是否被法庭采纳、选择的陪审团成员、陪审团的讨论、最终结果等所有上下文信息。
  用于为每个角色提供关于法庭上发生事情的上下文信息。

  注意：每个角色的发言正文会记录入法庭上下文，但是其思考内容只留在角色自己的上下文中不与任何其它法庭成员共享。法庭上下文中只记录对法庭上每个人都公开的信息。

- **法庭事件模拟**

  一组无状态的方法，用于串联角色和法庭上下文的交互事件。包括：

  - 挑选陪审团成员：随机产生 12 个陪审团成员录入法庭上下文（后期可扩展添加控辩双方对陪审团成员进行排除的过程）
  - 控方陈述：直接录入陈述内容到法庭上下文，不触发任何交流
  - 辩方陈述：直接录入陈述内容到法庭上下文，不触发任何交流
  - 控方举证

    - 对于证人：首先完成辩方律师与证人的问答。然后将证人信息、辩方问答、预设的控方问答、法官问答作为输入，触发法官对证人证词的裁决，裁决过程中法官可以通过工具调用询问控方、辩方和证人（（要求澄清、询问意见或继续提问）），最终输出是否采纳该证词的结论和原因。
    - 对于证据：输入包含证据内容和辩方质证意见。触发法官对证据的裁决，裁决过程中法官可以通过工具调用询问控方或者辩方（要求澄清或询问意见），最终输出是否采纳该证据的结论和原因。

    然后把这些信息录入法庭上下文。

    该事件可以进行多次，对每个控方证据进行一次。

  - 辩方举证

    输入包含辩方证据内容或证人信息。首先触发控方对证据发表质证意见。对于证人，质证期间控方可以通过工具调用询问证人问题，证人需要进行回答。
    
    然后将证据内容和控方质证意见作为输入触发法官对证据的裁决，过程类似控方举证，不过举证质证权利责任相反。最终输出是否采纳该证据的结论和原因。
    
    然后把这些信息录入法庭上下文。

  - 陪审团讨论

    每位陪审团成员基于已知信息和自己对案件的理解按顺序发表一轮评论。
    然后法官基于所有评论发表专业意见，可以补充必要的法律专业知识，纠正陪审团成员对信息的错误理解（比如以未被采纳的证据作为理由，未被采纳的证据应该完全排除）。
    然后每位陪审团成员进行投票（被告是否有罪）。如果投票达成一致则讨论结束，由法官综合所有陪审团成员的发言输出一份包含结果的陪审团综合意见。
    如果投票未能达成一致则重新回到讨论环节，继续 每位成员按顺序发言 -> 法官发言 -> 投票 的循环。直到所有陪审团成员投票达成一致。或者连续进行 10 轮仍为达成一致。
    如果最终结果是未能达成一致，那么仍然由法官输出包含未能达成一致的结果和陪审团成员的综合意见。

不包含：

- 法庭模拟系统本身不包含任何角色定义和案件定义。它们由 RoleProfiles 和 CaseProfiles 模块提供，在初始化时设置。
- 不包含游戏进程的驱动逻辑（比如什么时候应该由谁发表陈述、由谁举证），法庭模拟系统所模拟的法庭状态由外部调用驱动改变，但是可以包含一些必要的上下文校验（比如必须所有陈述、举证、质证都完成后才能进入陪审团评议，因为这是陪审团评议的必要）

上面提到的控方行为和辩方行为流程不完全一致主要是由于控方部分信息是案件定义中已经包含的，辩方信息是用户产生的。

### 2.1 角色上下文模版

System Prompt:

- 角色定义
- 案件公开上下文
- 案件私有上下文（可选）：只有这个角色知道的关于这个案件的信息，主要用于证人。证人不一定需要 100% 诚实，可以有自己的秘密。
- 法庭任务上下文：这个角色与法庭的关系，其今天到庭的主要任务是什么（比如“你今天到庭作为陪审团成员参与裁决该案件”）

User Prompt:

- 法庭上下文：包含在开始这轮对话生成前法庭上发生了什么事情的完整信息（谁说了什么、谁提交了什么证据等）
- 法庭指令和完成该指令所需的必要背景知识：比如“辩方提交了一份 xxx 证据，其上记录了 xxx ，辩方声称 xxx ，请对辩方提交的证据发表质证意见”

注意每一轮输入都包含完整的

## 3 角色定义 (RoleProfiles)

可插拔的关于游戏中法官、陪审团成员及候选人、控方代表、证人的角色定义。定义决定这些角色的表现、思维、行动风格。

每一个角色定义都包含其基础信息（姓名、性别、族裔等）、性格、人生经历、社会身份（工作、收入等）等信息定义。具体定义结构待定。

角色包含 3 大部分，在项目中的定义方式不同：

- 法庭成员

  包括法官、控方代表。系统应提供一组内置的默认预设，对于每个所需的角色有一份完整的定义。

- 陪审团候选人池

  为了提供充足的陪审团候选人，采用运行时随机组合的方式生成具体的候选人定义，而不是逐人完整预定义。

  但是仍需对构成完整角色定义的每个部分提供一组预定义选项。
  比如若干男性 First Name 、若干女性 First Name 和若干 Last Name 用于组合姓名，若干可以组合的性格、人生经历片段用于组合完整性格描述。
  工作、族裔、收入、年龄等在真实人群中具有分布特征的项除了需要提供可选列表，也要添加权重定义。收入、年龄等数值可以使用数值段+权重进行定义。

- 案件证人

  证人需要逐个完整定义，但由于证人与具体案件相关，因此属于案件定义的一部分。

系统默认预设应使用 YAML 格式在项目中集中定义，便于集中查看和修改，每个完整的角色定义一个文件，陪审团候选人池一个文件。在代码中引用这些定义。

## 4 案件定义 (CaseProfiles)

可插拔的关于游戏中模拟审理的案件的定义。定义决定法庭模拟系统向游戏内角色、玩家展示的案件相关信息内容。

每一个案件定义应该包含以下内容：

- 案件背景信息

  在审理开始前法庭上所有人应该周知的关于案件的已知信息。它是完全中立的，只包含无争议的事实（比如案件导致几人死亡），不包含尚待证明的推论（比如凶手就是被告）。

- 控方陈述

  控方对案件过程的理解，认为被告有罪的理由，建议的量刑等。

- 辩方陈述

  任何可以在法庭上进行陈述的内容，目的是表明被告无罪或轻于控方指控的罪。

- 证据、证人

  按顺序定义的若干证据、证人。控方和辩方的证据、证人列表分别定义。控方证据、证人用于证明被告犯有控方指控的罪，辩方证据、证人用于证明被告无罪或轻于控方指控的罪。

  证据定义包含：
  - 引用方对该证据的解释。包含：证据与案件的关系，在什么时间、什么地点、通过何种方式取得，引用该证据是为了证明何事等
  - 证据的客观描述（具体是什么，什么样）

  证人定义包含：
  - 引用方对该证据的解释。包含：证人与案件的关系，引用该证人是为了证明何事等
  - 控方、法官对证人的提问和证人的回答
  - 证人的角色定义（见 RoleProfiles ），用于驱动证人回答玩家作为辩方律师的提问
  - 证人自己真实了解到的案件相关信息（比如目击内容）这不会直接提供到法庭上，只用于驱动证人回答玩家作为辩方律师的提问

案件定义中由辩方律师提供的陈述、解释等内容用于向用户提供一个默认选项，用户在游玩时提出前可以按需修改。

系统默认预设应使用 YAML 格式在项目中集中定义，便于集中查看和修改，每个案件一个目录，其中按合理结构组织文件。
